# Jerrymapping fork notes, reference v0.1
Authority: 0-Jerrymapping-the-game.md (beta 0.1). This reference implements it as one game: panels never retire, the land freezes once painted, reworks decorate, anomalies alone command the rock.

## Deltas from The Endless Map reference
* One mode, always on (the book's semi-living game). Standard, Living Map, Living Deck machinery removed from play.
* Work numbers: single, as printed (the community ruling). The paint/rework split is NOT implemented.
* Farmland intensity: d4, 1-2 low, 3-4 high.
* Growth roll 5-6: climb, else sprawl; no farmland intensify fallback; a failed step reworks the town.
* Add Panel carries the shuffle: the deck shuffles after every Add Panel visit. The era-one cycle marker retires once Add Panel wakes (end of era one).
* Volcano: the ring becomes hills; settlements on the ring are destroyed.
* An impossible settlement reworks its rolled unit (blank ground still leaves a waymark).
* Vocabulary: panels, ages, reworks, in every log line.

## Simulator policies for the book's open choices
Choices are resolved by the reference's pick convention (logged). The rework-on-full walk uses the rolled-start consecutive walk. Wonder marks the rolled unit. Ruins and oasis use distance 3 for "far". The healing's artistic-freedom clause is human-only; the engine applies only the coastal-to-plain rule. The late-game pass-over option and the optional archive are not implemented in v0.1 (both are player options; dials can follow).

## Tuning dials, v0.2
Three dial families join the config and CLI. All defaults reproduce the handbook's game exactly (byte-identity verified against v0.1); the dials exist for exploration sessions like the Calm deck's.
* stroke_die (4) and stroke_add (1): the rolled stroke length, die plus bonus, at every d4+1 site: basin seed strokes, basin grow, free strokes, and extend's inward carry. Ridge lengths stay the player's choice. Measured flavor: d6+2 lifts water to about 46 and ocean unity to 73: longer strokes, bigger seas.
* greatridge_die (none) and greatridge_add (0): a simulator policy dial. The handbook's Great Ridge length is chosen, 4 to 10, and that stays the default; setting a die makes the engine roll instead. Analog players always choose.
* extend_cap (4): runs of cap or more count the same in Extend's contest; 0 or empty removes the cap and the true longest run wins.
Config compatibility warning: configs exported before v0.2 may carry these keys as inert leftovers; after v0.2 they are live. In particular greatridge_die 4 with add 2 in an old export would roll 3 to 6 instead of the chosen 4 to 10. Re-export, or delete keys you did not set deliberately.

## The archival dial, v0.3
* archive_chance (default 0): a percent, 0 to 100. When a panel first becomes complete, roll the chance once (a logged chance line); on success the panel goes to the Atlas: it leaves the visit rotation and never returns, logged "panel N COMPLETE, to the Atlas". Visiting an already complete panel never rolls. At zero the dial sleeps and the game is byte-identical to v0.2.
* World-state policy: archival removes the panel from rotation only. Its paint, people, and constraints remain part of the world for every rule (the Step Rule, fill counting, the settlement zone): the binder is storage, not erasure, exactly as retired panels always behaved in the parent lineage.
* The era row gains an "archived" clause only when the dial is set. The stack-empty free panel rule is the safety net under heavy archiving, and it is also the growth accelerator the handbook's growth knob describes: archiving drains the rotation, the stack empties sooner, free panels arrive.

## The portable RNG, v0.4: the C++ contract
Every random draw flows through one generator with one specification, so any port can be bit-exact. New world lineage: seeds speak a new dialect; the game is statistically unchanged.
* Generator: PCG32. 64-bit state, multiplier 6364136223846793005, fixed stream: increment (54 << 1) | 1. Seeding: state = 0; advance once; state += seed (mod 2^64); advance once. Output per advance: old = state; state = old * multiplier + increment (mod 2^64); xorshifted = ((old >> 18) xor old) >> 27, as 32 bits; rot = old >> 59; output = rotate right 32(xorshifted, rot).
* bounded(n), uniform 0 to n-1: threshold t = 2^32 mod n; draw r until r >= t; return r mod n.
* die(n) = 1 + bounded(n). pick(sorted seq): one element consumes no draw; otherwise seq[bounded(len)]. shuffle: Fisher-Yates from the top, i from len-1 down to 1, j = bounded(i+1), swap. chance(p): m = round(p * 1000) per-mille, computed once at config time; hit iff next < (m << 32) / 1000, integer division. The engine is float-free; percents allow one decimal.

## v0.6: the experimental fields dial
* exp_fields (default FALSE, CLI --exp-fields): EXPERIMENTAL, handbook chapter 11, not canon. Two rules in one switch: (a) the density ladder ignores farmed units entirely, they never block a step, never support one (excluded from the crowd count), and are never subject to one when placed; (b) the farm growth step deepens an existing low field in the settlement if there is one, choice among them, logged "the field deepens", before clearing new ground.
* Rationale: farmland carries density zero, so in a frozen-land game a field beside a home is a permanent cap on that home's density. Audited on a settlement-heavy deck: 67 fields against 44 rural, urban high absent from four worlds in five, and of every blocked climb 27 were blocked by a field.
* Measured with the dial ON, five seeds, twenty eras. Starting deck: fields 34 to 23, medium 2.8 to 8.4, high present in 4/5 worlds instead of 1/5. Settlement-heavy deck: fields 67 to 35, medium 2.8 to 11.2, high in 5/5 worlds.
* Rejected on measurement: fields climbing the ladder into rural (works, but farmland asymptotes to one field per world); building over fields as a fallback (never fires); building over fields as a preference (rural triples, high cities everywhere, the game becomes a city builder); keeping fields off the city edge (fields rise to 71, no effect on cities).
* Defaults are byte-identical to v0.5: the canon oracle lineage is untouched. If the experiment is promoted, the switch disappears, the rules move into the chapters above, and THAT is the lineage break.

* v0.6.1, a log-text bug fix: the Add Panel placement line printed the Manhattan sum instead of the squared distance score the engine actually uses (book chapter 9, squares, circular growth). The scoring itself was always book-correct; only the printed number lied. Display-only, worlds unchanged; log fixtures regenerate. Found by a community log reading at era 105. Lesson: the twin gate proves twin equality, not book conformance; a book-conformance test suite is the mitigation.

## Lessons from the v0.7 housekeeping increment
* THE GATE EXERCISES HAPPY PATHS ONLY. It compares runs that start from a seed and finish. Error paths produce no bytes to compare, so they are structurally invisible to it. Found the hard way: the web WASM flavor was built without exception support, so a refused load aborted the whole engine instead of returning an error. In a browser that ends the tester's session and any unsaved world with it. The node flavor, the one the gate actually runs, carried the flag; the flavor players use did not.
* Consequence: the two WASM flavors are built from one source with two flag sets, and flag divergence is invisible to every check the repo has. Mitigations for a future increment: assert build-flag parity between the flavors, and add a small web-flavor error-path suite (foreign lineage, malformed state, truncated document, out-of-range config) asserting graceful refusal rather than abort.
* A reusable property for conformance work: the genesis deck is shuffled once and the first card played becomes the cycle marker, so the ages before the first marker cycle are exactly one full pass of the deck. The starting deck's printed work numbers are therefore derivable from the log alone, which is how chapter 5's table became an assertable check.
* Conformance checks are written from the book's words, never from the implementation's behavior: a check derived from the code only restates what the code already does. Recorded as law in CONTRACTS 8.5.

## v0.7.1: the patina placement fix (render only)
* Found by a community reading of a panel image against its log: a spirit flourish appeared on a unit that was still blank when the flourish was recorded.
* The engine was right. When an instruction cannot be executed it becomes a flourish recorded AGAINST THE PANEL, with no unit chosen, because on a real map the player chooses where it goes ("trace your richest border" is guidance to the human). The log correctly prints no coordinate, and the turn order was correct: instruction first, then the work fill.
* The renderer was wrong. It distributed panel level flourishes over the panel's units in reading order starting at index 0, so EVERY panel's first flourish landed on its top left unit, whether or not that unit was painted. Measured over 20 seeds: 1804 panel level marks placed, 477 panels starting at the corner, 7 marks landing on ground that was never painted and therefore silently dropped, so the picture and the patina count disagreed.
* The rule now: panel level flourishes are placed on PAINTED units only, richest first (most already reworked), then round robin. On full panels the look is essentially unchanged, which is where most patina lives. Log bytes are unchanged; this is not a lineage break.
* Standing lesson: the renderer had never been audited. The gate compares logs, the conformance suite reads the book, and neither one looks at the picture. Any rule that exists only in a renderer is unreviewed by construction, and the app's canvas carries its own copy of this one (CONTRACTS 2.4, the patina rule).

## The teeth rule (from the v0.7.1 render checks)
* A new check must be DEMONSTRATED TO FAIL against the bug it was written for, before it is trusted. A check that has never failed proves nothing: it may be asserting something the code cannot violate, or looking at the wrong picture.
* Earned in practice: the render checks were pointed at the pre-fix twin and did fail on eight seeds, and that exercise exposed a flaw in the checks themselves, two of which examined only the engine's map and would have passed a buggy renderer. They now compare both pictures.
* This is the companion to the conformance rule in CONTRACTS 8.5. That one says a check must be written from the book, not the code. This one says a check must be proven able to fail.
* Still open from the earlier lesson: source-list parity between the WASM flavors is now closed by globbing, but the web-flavor ERROR-PATH suite (foreign lineage, malformed state, truncated document, out-of-range config) has not been written. Error paths remain invisible to the gate.

## Corrections and rules from the v0.8 review
* NAMING, corrected: the figure these notes have called "reworks per panel" since v0.1 is the EMBELLISHMENT STEPS per panel (the embellish counter divided by panel count). The engine keeps a separate reworks counter, which reads about 71 per panel where embellishment reads about 96. Two numbers travelled under one name. The comparisons in these notes all remain valid, including the parent-game one, because every one of them used the embellishment metric on both sides, but the label was wrong throughout and is now "embellishment steps per panel".
* THE BAND RULE EXTENDS BEYOND WATER. Urban high is the second high-variance statistic caught: sd 5.6 across a band of 0 to 24. Before quoting any per-world count as a single number, check its spread across seeds. Panels and embellishment steps are stable at three to five seeds; water and people counts are not.
* PAIRED COMPARISON is the method for any before-and-after claim: build the previous engine and run the SAME seeds through both, rather than comparing two measurements taken on different seed sets. A seed-set difference, not a disagreement about the game, produced the 18-of-20 against 15-of-20 gap above.
* A VALUE A CALLER CAN SUPPLY MAY NEVER REACH AN ASSERT. Earned by the error-path suite on its first run: a config with an impossible geometry was accepted, built a world, and hit an assertion inside the first age, aborting the engine in the browser. Validation belongs at the one place every surface passes through, and it must reject with a message rather than trap. Same family as the missing exception flag, and invisible to the gate for the same reason: the gate only ever runs configurations that work.

## The primed eye (a review lesson from the digitalizer sessions)
* During a live review session, a feature request to "add a notes field" primed the reviewer to find the field missing, and the session reported it absent even though the reviewer's own screenshot showed the field on screen, labeled. The element dump was read through the request's assumption instead of on its own terms.
* The rule: a manual session's finding must quote its evidence, not its conclusion, and when a live test confirms a request's premise too neatly, re-read the evidence before reporting. A request to add X is also a hypothesis that X is missing, and hypotheses are for testing.
* Companion to the teeth rule: that one guards automated checks against never failing; this one guards human review against finding what it was sent to find.

* THE BLUR WAS NOT IN STORAGE. Observed on 2026-08-08 at commit 0e1ce94, on the tester's own donated archive. All 40 stored scans still carry the authoring metadata of the tools that made them (Exif, plus a Photoshop block or an ICC profile with XMP), which a canvas re-encode always strips. The import-as-is path returns the uploaded File itself when the picture is within 4096 px and is a png, jpeg or webp, so the bytes on disk ARE the bytes uploaded. Round trip through the digital-file upload path, all 40 images: SSIM 1.0000, bytes unchanged, Laplacian variance unchanged. The acceptance metric this session was given was already at its ceiling before any change, which is worth stating plainly rather than hiding behind a passing table.
* THE BLUR WAS IN THE VIEWING SURFACE. The atlas draws 256 px thumbnails and lets the map be pinched to 4x. Measured in the running app: at about 2x zoom on a phone-shaped viewport at device pixel ratio 3, a 213 x 256 thumbnail was painted into 567 x 683 device pixels, an upscale of 2.66, while the sharp 884 x 1062 scan sat unused in the database. At the atlas maximum of 4x the upscale reached 3.12 at ratio 1.75. That is the softness the third field report describes, and no storage change could have touched it.
* THE FIX, AND ITS BOUND. Past 1.5x zoom, a visible atlas cell asks for its stored scan instead of its thumbnail. Same panel, same 2x zoom, same phone viewport, after the change: source 884 x 1062, upscale 0.64, meaning the image is now being downsampled into the cell instead of stretched. The scans live in a pool that holds at most 12 of them, evicts the least recently wanted, and revokes that object URL as it goes; a cell whose scan is evicted hears about it and falls back to its thumbnail, so no image element is left pointing at a revoked URL. The ceiling does not grow with the map: a 280 panel world still holds twelve, which is roughly 45 MB of decoded pixels in the worst case and about 4 MB of compressed blobs. Storage on disk is untouched, which is the point: the fix costs no bytes at all.
* THE PHOTO PATH STAYS LOSSY, DECIDED 2026-08-08. Crop and straighten re-encodes to WebP. Measured over the same 40 images: SSIM 0.9791, 0.9817 and 0.9884 by map, bytes cut to roughly a third (366 KB to 168, 183 to 50, 165 to 54 per panel), and sharpness held: Laplacian variance 1603 to 1588, 838 to 839, 575 to 571. The loss is chroma detail, not softness. Accepted as it stands, because the tester's own uploads never take this path and the byte saving is real. If pre-upload originals arrive, the paired source-against-stored mode may revisit this with real photo ground truth. That is a door, not a promise.
* AUTO-FIX IS DETERMINISTIC, MEASURED. The same input twice gives byte-identical output on all 40 scans, and all 40 still match the goldens captured before the session's change. The goldens are one picture per map plus a hash for every scan, in apps/pwa/tests/goldens/autofix-sandy-r3/. Nothing needed explaining, because the fix was display-side and the stored bytes never moved.
* WHY AUTO-FIX BEATS THE SLIDERS, since the tester calls it close to magic. Exposure, contrast and temperature are global curves: one lookup table applied to every pixel alike. Auto-fix is not a curve at all. It estimates the illumination across the frame by shrinking the picture about 24 times, blurring it twice, and growing it back, then divides every pixel by that local estimate. Because the divisor varies from place to place, a shadow band, a vignette and a warm corner all flatten in the same move, and no global slider can do that, since a single curve cannot brighten one corner while leaving another alone. Because the division runs per channel, a color cast that changes across the paper is corrected too. Because the target is a constant near white, the paper itself defines white rather than a number the player has to guess, and ink survives because ink differs from its LOCAL background, not from the image mean.
